# 태스크 공유 아키텍처 설계

> 상태: **설계 제안(미구현)**. 채팅에 태스크를 공유하고, 태스크의 변경을
> 참여자 화면에 반영하는 기능의 설계 근거를 남긴다. 지금 있는 동기화 원리
> (스냅샷 + `sync_seq` + tombstone + 커서 델타)를 그대로 재사용한다.

## 목표와 범위

- 태스크를 채팅(대화)에 **메시지 형태**로 공유한다.
- 공유 이후 원본 태스크가 바뀌면(제목·날짜·상태·삭제) **참여자 화면에 반영**한다.
- 지금의 유저 단위 동기화를 **깨지 않고**, 나중에 얹을 수 있는 이음새만 확보한다.

## 현재 동기화가 이미 가진 원리 (재사용 대상)

공유 설계는 새 메커니즘을 만들지 않는다. 다음 네 규칙을 scope만 바꿔 재사용한다.

| 원리 | 위치 | 하는 일 |
|------|------|---------|
| scope 락으로 직렬화 | `platform/db/sync.ts` `withUserSyncSeq` | 발급 순서 = 커밋 순서 → 커서 구멍 제거 |
| scope 카운터 +1 → 행에 `sync_seq` 도장 | `sync_counters`, `schema.ts:52` | "몇 번째 변경인지"를 행에 박음 |
| 커서 뒤(`sync_seq > cursor`)를 순서대로 | `adapters/sql.ts` `changesSince` | 놓친 것 없이 순서대로 재생 |
| 스냅샷 upsert / tombstone remove | `use-task-sync.ts` `applyDelta` | 종류 판별 없이 최신 상태로 수렴 |

핵심 성질:
- 행당 **최신 스냅샷 하나**만 든다. 과거 상태·과거 seq는 안 남긴다(제자리 덮어쓰기).
- 삭제는 행 삭제가 아니라 `deleted_at` **tombstone**이라, 삭제도 델타에 실려 전파된다.
- 신호(SSE)는 힌트일 뿐 **커서가 진실**이다. 신호 유실·중복은 무해하다.

## 설계 결정 1 — 메시지는 "값 복사"가 아니라 "참조 + 폴백 스냅샷"

| | 값 복사(snapshot) | 참조(reference) | **채택: 참조 + 폴백** |
|---|---|---|---|
| 담는 것 | 공유 시점 필드 전부 | `taskId`만 | `taskId` + 공유 시점 스냅샷 + `snapshotSeq` |
| 수정 반영 | ❌ 박제됨 | ✅ | ✅ 라이브로 최신화 |
| 삭제 반영 | ❌ 그대로 남음 | ✅ | ✅ tombstone 상태로 |
| 오프라인·권한상실 | ✅ 보임 | ❌ 빈칸 | ✅ 스냅샷 폴백 |

메시지 payload:

```ts
{ taskId, ownerId, snapshot /* 공유 시점 값 */, snapshotSeq /* 그때 sync_seq */ }
```

`snapshot`은 "즉시 표시 + 폴백"용이고, **진실은 라이브 태스크**다.
("신호는 힌트, 커서가 진실"과 같은 구조 — 여기선 "스냅샷은 폴백, 라이브가 진실")

## 설계 결정 2 — 카드 렌더링은 기존 `applyDelta`와 같은 판정

임베드 카드는 종류(추가/수정/삭제)를 따지지 않고, `taskId`로 라이브를 조회해
`sync_seq`로 신선도만 판정한다.

```
1. taskId로 라이브 태스크 조회
2. 라이브 sync_seq > snapshotSeq  → 최신값으로 그림 + "수정됨" 표시
3. 라이브 deleted = true          → "삭제된 태스크" 상태 (메시지는 남기고 카드만 tombstone)
4. 라이브를 못 읽음(권한/오프라인) → snapshot 폴백
```

`sync_seq`는 **같은 task의 seq끼리만** 비교한다(유저 간 절대값 비교 금지 — 아래 참고).

## 설계 결정 3 — 동기화 scope: 유저 단위를 두고 "대화 단위"를 나란히 얹는다

### 원리: scope = "한 커서로 구독하는, 여러 독자가 공유하는 읽기 집합"

커서(스칼라 하나)가 성립하려면 그 스트림의 **모든 항목이 커서 주인에게 보여야** 한다.
안 그러면 (a) 안 보이는 변경이 새고, (b) 커서가 못 받은 변경을 지나쳐 구멍이 난다.

- 개인 데이터에서 그 단위는 **유저** (독자가 자기 하나) — 현재 설계.
- 공유 데이터에서 그 단위는 **대화** (독자 = 참여자 전원, 같은 집합을 봄).

### 왜 대화 단위인가 — 후보 비교

| 후보 | 문제 | 판정 |
|------|------|------|
| 소유자의 user 카운터를 그대로 | 참여자에게 안 보이는 task가 seq 공간에 섞임 → 유출·커서 오작동 | ❌ |
| per-task 카운터 | 커서가 스칼라 불가(벡터 클럭 필요), 새 task 발견 불가 | ❌ |
| 수신자(user) 단위 카운터 | task 하나 수정에 독자 수만큼 카운터 +1 (fan-out-on-write) | ❌ |
| **대화(conversation) 단위 카운터** | 참여자 N명이 카운터 1개 공유, 수정당 +1 한 번, 새 항목 발견 자동 | ✅ |

대화는 정의상 "고정된 참여자 집합이 같은 콘텐츠를 함께 보는 최소 단위"라,
per-user와 **완전히 같은 그림**을 키만 `user_id` → `conversation_id`로 바꿔 얻는다.

### 왜 per-task로 "미리 옮기면" 안 되는가

per-task는 미래 대비가 아니라 **롤업 커서를 풀어헤친 가장 비싼 극단**이다.

- 커서가 스칼라 하나로 안 됨 → `{taskId: seq}` 벡터 클럭 필요(태스크 수만큼 칸).
- 처음 보는 task는 커서 맵에 없어 **존재조차 모름** → "내 task 목록"을 따로 동기화해야
  하는데, 그게 지금 per-user seq가 공짜로 해주던 일이다.
- 공유가 원하는 건 per-task seq가 아니라 **접근권(누가 읽나) + scope 하나 추가**다.

### 한 task가 두 scope에 잡히는 것은 정상

공유된 task를 수정하면 **소유자 user 카운터**(본인 기기 동기화)와
**대화 카운터**(참여자용)가 둘 다 +1 된다. 서로 다른 독자 그룹을 위한 서로 다른
스트림이라 양쪽 다 정확하다. 이것이 "per-user를 놔둔 채 per-conversation을
나란히 얹는다"의 실제 모습이다.

## 반영 절차 (요약)

```
공유:  메시지에 { taskId, ownerId, snapshot, snapshotSeq } 저장
        + 접근권(grant) 생성: "이 대화 참여자가 이 task를 읽을 수 있다"

본인 화면:   기존 user 델타에 그 task가 이미 실려 옴 → 카드가 taskId로 최신 캐시를
             읽게만 하면 자동 최신화 (추가 작업 거의 없음)

참여자 화면: 대화 카운터/커서로 델타 수신 → 카드가 sync_seq로 신선도 판정
             → 최신값 / "수정됨" / "삭제됨" / 폴백 렌더
```

## 나중에 얹을 것 vs 지금 확보할 것

### 나중에 (공유 모델 확정 후)

- `share_grants` 류 접근권 테이블: `task_id | conversation_id | ...`
- `withConversationSyncSeq` (= `withUserSyncSeq`를 scope만 바꿔 복제)
- 참여자용 라이브 read 경로: `where user_id = 나` → `where 내가 접근권 있는 task`
- 갱신 푸시를 개인 sync가 아니라 **대화 채널**로 fan-out

> 조기 일반화 금지: 공유 모델(참여자 규칙·권한 회수)이 확정되기 전에 미리 파면
> scope마다 "발급 순서 = 커밋 순서" 정합성을 다시 증명해야 하고 틀린 추상을 굳힌다.

### 지금 (미래를 안 막는 저비용 이음새)

1. 임베드를 **값 복사로 박제하지 말 것** — 처음부터 `taskId` 참조 + 폴백 스냅샷으로.
2. `withUserSyncSeq`를 지금처럼 **scope 하나에 깔끔히 묶인 형태**로 유지
   (그대로 `withConversationSyncSeq`로 복제할 수 있게).
3. 카드 신선도는 **같은 task의 `sync_seq`끼리만** 비교 — 유저 간 seq 절대값 비교는
   금지(각 scope가 각자 1,2,3…). 대화 단위 커서가 필요해지면 그때 도입.

## 열린 결정 (구현 착수 전에 정할 것)

- 실시간 범위: **A. 본인 화면만 최신**으로 충분한가, **B. 모든 참여자 실시간**까지 필요한가.
  A면 지금 machinery로 거의 끝, B면 대화 scope + 공유 채널이 필요하다.
- 접근권 회수(공유 취소) 시 이미 뿌린 카드의 처리: tombstone 유사 "접근 종료" 상태로 둘지.
- 대화 scope 커서를 참여자별로 둘지, 대화별 단일 스트림 + 참여자별 커서로 둘지.
