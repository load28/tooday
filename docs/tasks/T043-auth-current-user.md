# T043 — 현재 인증 사용자 API를 auth.getCurrentUser로 명확화

## 배경

user.me는 프로필 전용 API가 아니라 익명도 정상 응답하는 세션 프로브다. T031의 반복 요청 해결과 갱신 경로를 유지하면서 이름과 소유권을 맞춘다. 세션·프로필 API 분리는 폭포수 요청을 추가하므로 채택하지 않는다.

## 작업 내용

- auth.getCurrentUser로 단일 조회를 이동하고 sessionProcedure 및 응답 의미를 유지한다.
- 사용자 조회 어댑터는 유지하며 조립 계층에서 인증 모듈의 조회 포트에 주입한다.
- 공유 응답 계약, 웹 transport, 테스트, 현재 아키텍처 문서를 정리한다. 과거 태스크 기록은 보존한다.

## 완료 기준

- [x] 익명 200+null, 무효 인증 401, 유효 인증 사용자 반환 및 private 캐시 유지
- [x] 기존 클라이언트 호출 경로와 계약 이름 갱신
- [x] 타입·경계 검사 및 인증 관련 테스트 검증

## 대화 기록

> **사용자**: 분리하면 대신 두개의 api가 폭포수 모델로...요청이 필요하군

> **어시스턴트**: 맞아요. **세션 확인이 끝나야 `user.me`를 요청한다면 폭포수 요청이 됩니다.** 제가 제안한 분리는 역할은 명확하지만, 초기 요청 비용이 늘어나는 단점이 있어요.
>
> 그렇다면 이 프로젝트에서는 **API를 분리하기보다, 지금 API의 실제 역할에 맞게 이름을 바꾸는 편이 낫겠습니다.**
>
> 예를 들어 기존 `user.me`를 **`auth.getCurrentUser`**로 바꾸는 거예요.
>
> - 로그인 상태 → `200 { user }`
> - 인증 정보 없음 → `200 { user: null }`
> - 인증 정보가 있으나 무효 → `401`, 기존 갱신 경로 유지
>
> 이 API의 질문은 “로그인한 내 프로필을 가져와”가 아니라 **“현재 인증된 사용자가 누구인지 알려줘. 없으면 없다고 알려줘”**입니다. 사용자 정보까지 한 번에 반환하므로 별도 프로필 요청도 필요 없습니다.
>
> **역할을 명확하게 한다고 반드시 요청까지 분리할 필요는 없어요.** 여기서는 기존 동작과 캐시 구조를 유지하고 이름을 바로잡는 것이 가장 작은 변경으로 의미를 명확하게 만드는 방법입니다.
